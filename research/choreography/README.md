# research/choreography: the choreography lab

Where light shows are tried, compared and judged, without touching the installation. Design:
`research/analyzer_trials/papers/P3_choreography_contract.md` (draft, not answered by the owner yet).

There is no ground truth for a show. A mode is judged in three layers: laws (the existing mode tests),
measures (numbers that filter out what clearly fails), and the owner's choice between versions of a clip.
Only the owner's choice promotes a mode.

## What is here

| File | Role |
|---|---|
| `layout.py` | the 11 segments and the room position of the 1,304 LEDs, from `config/segments_full.json` |
| `feeds.py` | what a mode under test hears through `listener.signals`: the truth, an analyzer's recording, or nothing extra |
| `render.py` | plays a song through the production `Listener` (5 s look-ahead), lays the feed over its signals, and draws one mode instance per segment |
| `measures.py` | first measures: kick punch, alive |
| `build_clips.py` | renders a passage and writes a clip (frames, audio, `meta.json`): one mode once per feed, or two modes on the same feed (`--against`) |
| `profile.py` | what the light does on a passage, in numbers and in words: amount of light, reaction to a kick, a snare, a drop, behaviour in a break, where the light sits, colours, flicker, repetition |
| `pictures.py` | stills an agent can read: the time strip, the contact sheet, the reaction curves |
| `profile_clip.py` | profiles every version of the clips already built (`output/profiles/<clip>/PROFILE.md`) |
| `check_mode.py` | the gate: five pass/fail rules a mode must meet before the owner is asked to look at it |
| `nominate.py` | puts clips of a gated mode in the owner's queue; `--rebuild` draws queued clips again |
| `status.py` | writes `STATUS.md`: where every lab mode stands and what waits for the owner |
| `records.py` | reads and writes the three small records below, and holds the "waiting" rule |
| `clip_server.py`, `clips.html` | the page where the owner watches versions side by side and chooses. Waiting clips come first |
| `candidates/` | lab modes. Not registered, never run on the installation |
| `verdicts.jsonl` | every choice the owner makes, appended. Committed: it is the owner's word |
| `queue.json` | the clips nominated for the owner. Committed. An entry waits until a verdict line names its clip |
| `gates.json` | the latest gate result of each mode. Committed (the full reports are in `output/`, which is not) |
| `STATUS.md` | generated by `status.py`. Committed. Do not edit by hand |

## Use

    research/analyzer_trials/.venv/Scripts/python.exe -m research.choreography.build_clips --defaults
    research/analyzer_trials/.venv/Scripts/python.exe -m research.choreography.clip_server

then open http://127.0.0.1:8768 (or start `choreography-clips` from `.claude/launch.json`). About 15 s to
build a clip. Clips go to `output/` (not committed: they contain audio). Tests:
`python -m pytest research/tests/test_choreography_lab.py research/tests/test_choreography_profile.py research/tests/test_choreography_cycle.py tests/governance/test_lab_isolation.py`.

## One cycle, for an agent working alone

The full procedure is `.agents/skills/vialactee-choreographer/SKILL.md` (launch: `/light-cycle`). The work list is
`BACKLOG.md`. An agent keeps its own scripts and notes in `runs/<Mode_name>/`. What a lab agent may change is
checked by `python -m research.guard check choreography`. A nomination and every choice of the owner rebuild
`STATUS.md` and the owner's page `research/INBOX.md`.

All commands run from the repository root. `PY` stands for `research/analyzer_trials/.venv/Scripts/python.exe`.

    PY -m research.choreography.check_mode My_mode            1. the gate (builds and profiles the three standard passages)
    PY -m research.choreography.nominate My_mode --against Power_bar_mode --note "what to look at"
                                                              2. only if the gate passed: clips go to the owner's queue
    PY -m research.choreography.status                        3. rewrite STATUS.md

1. **Write the mode** in `candidates/My_mode.py` (file name = class name).
2. **Run the gate.** It takes about two minutes. It prints the five results, writes
   `output/gates/My_mode/GATE.md` (read it: the result first, then every number) and the mode's line in
   `gates.json`. Exit code 0 = passed, 1 = failed, 2 = the gate could not run (no such mode, a missing song).
   The gate also leaves the full profile with pictures in `output/profiles/<clip>/PROFILE.md`.
   `--reuse` skips the drawing when the clips were already built from the mode's current code.
3. **If it failed, change the mode and run the gate again.** Never change a limit to make a mode pass.
4. **If it passed, nominate.** Without `--against`, the owner compares the feeds of your mode. With
   `--against Other_mode`, the owner compares your mode with another one (a lab mode or a registered mode from
   `modes/`), both hearing the same feed (`--feed today`, the default, or `truth`, or `candidate`).
   `nominate` refuses a mode that never went through the gate, failed it, or changed since. Exit code 1 = refused.
5. **Run `status`** and commit `gates.json`, `queue.json` and `STATUS.md` with the mode.
6. **Wait for the owner.** Only the owner's choice on the clip page says a show is good.

To build single clips by hand, without the gate or the queue:

    PY -m research.choreography.build_clips --mode My_mode --track 19 --start 208 --duration 24
    PY -m research.choreography.build_clips --mode My_mode --against Power_bar_mode --feed today --track 19 --start 208 --duration 24
    PY -m research.choreography.profile_clip [clip ids]

After a fresh checkout the queued clips are not on disk (they hold audio): `PY -m research.choreography.nominate --rebuild`
draws the waiting ones again (`--all` for the judged ones too).

## The gate

`check_mode.py` draws the mode on the three standard passages, on every feed, and answers five questions.
A mode passes when no rule fails. **Every limit is a provisional proposal, not a decision of the owner.** The
limits are named constants at the top of `check_mode.py`.

| Rule | In plain words | Fails when |
|---|---|---|
| 1. It runs | the mode draws every passage on every feed | any drawing stops on an error (the error is in the report) |
| 2. It works on today's analyzer | hearing only what the installation hears today, the light is neither stuck dark nor frozen | dark more than half of the time music plays, or the light travels less than 3% of full brightness |
| 3. Flash safety | no more than 3 general flashes in any one second (WCAG 2.3.1, as counted by the profile) | more than 3, hearing the truth or hearing today's analyzer, on any passage |
| 4. Tied to the music | on the control (every hit moved half a beat late) fewer flashes land on a real hit | the share of flashes on a real hit is not at least 20 points lower on the control than on the truth |
| 5. Cost | mean time to draw one frame of the whole installation | above 33 ms **on this PC** |

- Rule 2 counts a show as moving if either the whole installation or a typical single LED changes brightness, so
  a show that travels in space at a constant total light is not called frozen.
- Rule 4 answers "not applicable" (neither pass nor fail) when it has nothing to count: the mode does not
  flash, the passage has too few hits, or the mode draws exactly the same frames on the truth and on the
  control (it does not read the hits the lab feeds: every registered mode of `modes/` is in this case today).
- Rule 5 is only an indication. The installation draws 30 frames a second on a Raspberry Pi, which is several
  times slower than a PC. Above 5 ms the report asks for a timing on the Pi.
- Everything else the profile measures is listed in `GATE.md` as "reported, not judged".

## The owner's queue

`queue.json` is a list. One entry per clip:

    {"clip": "19_0208_My_mode_vs_Power_bar_mode_today_n1", "mode": "My_mode", "against": "Power_bar_mode",
     "feed": "today", "track": "19", "start_s": 208.0, "duration_s": 24.0, "nominated": "2026-11-27", "note": "..."}

`against` and `feed` are `null` when the clip shows the feeds of one mode. **An entry is waiting exactly when no
line of `verdicts.jsonl` has the same `"clip"` value.** Every nomination gets new clip ids (`_n1`, `_n2`...), so a
mode can be nominated again after the owner has judged an earlier version. Entries are never removed.

A verdict line keeps its first fields (`at`, `clip`, `choice`, `order`, `chosen_feed`, `labels_hidden`, `note`)
and now also says: `kind` (`"feeds"` or `"modes"`), `mode`, `against`, `feed`, and `chosen_mode` (the mode the
owner preferred in a mode-against-mode clip, else `null`). Lines written before these fields existed stay valid.

## How an agent sees a mode

An agent cannot watch a clip. After `build_clips`, run

    research/analyzer_trials/.venv/Scripts/python.exe -m research.choreography.profile_clip

and read `output/profiles/<clip>/PROFILE.md`: a table of the versions side by side, a paragraph in words per
version, and three pictures per version. Open the pictures: the time strip (time left to right, LEDs top to
bottom, truth marks above) shows in one look whether flashes fall on the kicks, whether a break is calm, and
whether anything travels. The profile says what a show does, never whether it is good.

## The feeds

The same mode is drawn on the same passage once per feed:

| Feed | The mode hears | It shows |
|---|---|---|
| truth | every signal of the contract, from the truth file | the best the idea can look |
| candidate | the signals a research analyzer produced on that song (the music lab's recording) | what the installation could do |
| today | the production analyzer as it is; empty slots fall back inside the mode | what the installation does now |
| control | the truth with every hit moved half a beat late | a version that is wrong on purpose. Not shown to the owner. A mode tied to the music must come out clearly worse on it |

Everything else the mode reads (energy, beat phase, mood colours) comes from the production `Listener` in
all three cases, so the versions differ only by the signals under test.

## Brightness, timing and safety

- **Brightness is what the eye sees.** The installation sends values to the LEDs unchanged (no gamma anywhere
  in `hardware/`), and an LED's light is proportional to the value, so a tenth of the value already looks more
  than a third as bright. `render.perceived` (CIE lightness) is applied to every brightness number of the
  profile, and the clip page and the pictures re-code the values so a screen shows them as the LEDs would
  look (`render.screen_values`; the page has a switch to see the raw values).
- **Timing is read at 60 frames per second**, and the profile reports when the light is halfway up, read
  between two frames. A light is noticed as late from about 45 ms after the sound, and tolerated up to about
  125 ms before it (ITU-R BT.1359, measured on television picture and sound, not on light flashes).
- **Flash safety** follows the general-flash rule of WCAG 2.3.1: a flash is a pair of opposing changes of 10%
  or more of full light, and there may be no more than three in any second. The profile counts them on the
  whole installation and on each third of its height and reports the worst. Saturated red flashes are not
  checked. The gate enforces it (rule 3).
- **False flashes are counted.** The profile finds the visible flashes in the light itself and says how many
  fall on a real kick, snare or drop, how many real hits get one, and how often it flashes during a break.

## Rules

- **The two labs never import each other** (`tests/governance/test_lab_isolation.py`). This lab reaches the
  analyzer only through `music.api`. What it takes from the music lab is data: the signal contract
  (`config/music_signals.json`), the truth files, and recordings whose columns are the contract's slot names.
- **A lab mode names a fallback for every signal it reads**, so it still works on today's analyzer.
- **A mode that reads a signal the installation does not have cannot be promoted** until that signal is there.
- **Measures filter, they do not rank.** The gate's limits filter out what clearly fails; they are provisional
  proposals until the owner decides them. A limit is never changed to let a mode through.
- **Only a gated mode goes to the owner**, and a gate counts only for the code it was measured on.
- **Choices are blind by default**: the page shuffles the versions and says which was which only after the
  owner has chosen. This holds for feeds and for mode against mode.
- **`verdicts.jsonl` is the owner's word**: lines are appended by the clip page, never rewritten or removed.

## Not built yet

- the "realistic" feed (truth degraded by a measured error profile);
- limits decided by the owner: the five rules of the gate use provisional limits, and the other numbers of the
  profile have none (they describe, they do not judge);
- flash safety for saturated red, and a cost measured on the Raspberry Pi instead of a PC;
- the lab steps the `Listener` 60 times a second and draws the mode on every step, while `core/Mode_master.py`
  updates and draws 30 times a second (see the session log of 2026-11-27): the lab is not yet faithful on this;
- "what drives it": the profile under the mute test (beat, level, spectrum, hits muted in turn);
- passages drawn at random on held-out tracks, hidden references, repeated pairs (the gate and the queue use
  the same three standard passages every time);
- a registered mode drawn as the installation draws it: the lab makes one copy of the mode per segment and has
  no `Mode_master`, so a registered mode that needs the installation's own set-up may look different here;
- a check against the real installation: the page is a drawing on a screen.
